## 結論

6ページの解説サイトを書き上げたあと、分かりやすさを主観で議論する代わりに3つの数を数えた。

1. **実際の入出力の例が何箇所あるか**
2. **同じ話題が何ページに出てくるか**
3. **用語集への被リンクが何件あるか**

この3つで、直すべき箇所と優先順位がそのまま出た。

## 1. 実例の数 — 全6ページで0件

```
実際の入出力の例を示している箇所: 全 6 ページで 0 件
```

これが最大の欠落だった。「なぜそうしたか」は各所に書いてあり、難しい概念には言い換えも
添えてあった。それでも、**「こう書いてトリガーすると、こういうものが返ってくる」という一連の
実物**がどこにも無い。

初めて読む人がこの手の仕組みを理解する経路は、たいてい抽象的な説明より先に
**入力と出力の実物を1回見ること**。構成の説明から始まると、読者は何が起きるのかを頭の中で
組み立てながら読むことになる。

トップに「入力 → 開始時の応答 → 完了時の応答」の3段を、架空の例で実物として置いた。
5つ挙げた改善のうち、これが効果としてはいちばん大きい。

## 2. 同じ話題が何ページに出てくるか

各キーワードを含むファイル数を数えるだけ。

| 話題 | 修正前 |
|---|---|
| worktree | 4ページ |
| 待ち行列 | 4ページ |
| 実行時間の上限 | 3ページ |
| tmux | 3ページ |

書いた側には「構成の話」と「時系列の話」という切り分けがあったが、**その区別を読者に事前に
伝えていない**。読み手には「さっき読んだ話がまた出てきた」としか映らない。とくに一番大きい
ページ（3,860字・見出し7個）が全部を抱え込んでいて、後続ページが要約の再放送になっていた。

対処は削除ではなく**宣言**。各ページの冒頭で守備範囲を1行で言い、末尾に次ページへの導線を
置いた。修正後は worktree が3ページ、tmux が2ページ、実行時間の上限の詳細は1ページに一本化。

ゼロにする必要はない。**役割が違うなら重複してよい**（説明・定義・別観点からの言及）。
問題なのは、役割の違いが読者に見えないこと。

## 3. 用語集への被リンク — 0件

```
用語集へのリンク: 全ページで 0 件
```

用語はすべて、用語集より前のページで初出する。そこからリンクが張られていないので、詰まった
読者はナビゲーションの端から自力で見つけるしかない。しかも本文側にも同じ説明を書いていたため、
**用語集が「詳しい定義」なのか「リマインダー」なのかが曖昧**だった。

見出しに明示的なアンカーを振り、本文の初出から張った。被リンク **0件 → 11件**。
冒頭に「通読は不要、詰まったら引く」と役割を明記した。

## ついでに見つかったこと

- **1ページだけ読者像が違った。** 他は「この仕組みを理解したい人」向けなのに、1ページだけ
  「これを運用する人」向け。しかも具体値を伏せているので手順としては使えない。
  「運用しやすくするための設計」に書き換えて読者像を揃えた
- **読み終わりの印象。** 「このサイトに書いていないこと」がトップの締めにあり、
  読了時の印象が「肝心なことは書いていない」になりかねなかった

## 一般化

「読みやすいか」は測れないが、次の3つは測れて、しかも測った結果がそのまま作業項目になる。

| 数えるもの | 0 や過大なら |
|---|---|
| 実際の入出力の例 | 抽象的な説明だけで構成されている |
| 同じ語を含むページ数 | ページの切り分けが読者に伝わっていない |
| 用語集への被リンク | 参照系のページが孤立している |

書いた本人には全体像があるので、重複も実例の欠落も見えない。数えると見える。
