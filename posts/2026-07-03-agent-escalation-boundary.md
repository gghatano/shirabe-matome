## 結論

一括修正をエージェントにやらせるときは、**「ここから先は直さずに止めて報告する」線を作業定義に文章で書いておく**。線が無ければエージェントは直せるものは直してしまう。今回は実際に線を越えるケースが1件出て、正しく停止・報告された。

## 引いた線

作業定義に書いたのは3行だけ。

- レビュー主導のギャップ修正とし、**最小差分**で反映する
- **合成データ（CSV）は再生成しない**
- 合成データの再生成が必要な FAIL は自動修正せず、`needs_human_review` として停止・報告する

要点は、線を「難易度」ではなく **「影響が下流に波及するか」** で引いていること。難しいかどうかはエージェントごとに判断がぶれるが、「データ生成に手が入るか」は機械的に判定できる。

## 実際に止まった例

1件で、こういう状態が見つかった。

- 使われていない生成スクリプトとその出力（CSV / PNG）が残っている
- それらが参照している ID が、確定版のマスタとは異なる**旧採番**のまま
- しかもシナリオ文書からは一切参照されていない孤児ファイル

直すには生成スクリプト側に手を入れて出力を作り直す必要がある。線の外なので、ワーカーは修正せず `needs_human_review` として報告して終わった。

これは「直せなくはないが、直すと影響範囲が読めない」典型。放っておくと不整合として残り続けるので、エージェントには直したい誘因がある。だからこそ明示的に止める必要がある。

## 直してよかったもの

同じバッチで自動修正されたのは、こういう種類。

- **参照 ID の双方向不一致** — 片方の文書には関連 ID が書かれているのに、もう片方に無い
- **仕様書に固定値で埋め込まれた件数** — 「31件」と書いてあるが実際は22件だった。生成スクリプト側を直して解消
- **旧 ID 体系からの移行メモの残置** — 「旧 DS-04-028/029 は … に再整理済み」といった過渡期の記述を、最終形ベースの説明に置換
- **評価値の機械再算出との不一致** — 再算出したら4件が現行のマスタと食い違っていたので補正（最終判定そのものは変わらず）

共通しているのは **正しい値が機械的に一意に決まる**こと。どちらが正かを人が決める必要がなく、下流の再生成も発生しない。

## 判定できないものを断定させない

もうひとつ、同じ思想の設計。

参考リンクの到達確認で、あるページが WebFetch に対して **403** を返した。ワーカーはこれを「リンク切れ」と断定せず、bot 拒否の可能性があるとして**改善推奨として記録するに留めた**。これが正しい。403 は「そのリンクが死んでいる」ことを意味しない。自動リンクチェックで 403 を死亡と数えると、bot 対策をしているサイトが軒並み誤検出になる。

一方で、同じ確認で実際に修正されたものもある。参考 URL 4件がロケール違いのパス（`en_w/...` のような形）になっていて、目的のページに到達していなかった。こちらは**到達しないことが確認できている**ので修正対象。

到達しない（=事実）と、到達できなかった（=判定不能）を分けて扱う。自動化した検査は、判定不能をそのまま「判定不能」として残せるかどうかで信頼できるかが決まる。全部を白黒に丸めた瞬間、出力を人が読み直す羽目になる。

## まとめ

線は3種類に分かれた。

| 種類 | 扱い |
|---|---|
| 正しい値が機械的に決まる | 自動で直す |
| 直すと下流の再生成が波及する | 止めて報告する |
| 正否の判定自体ができない | 判定不能のまま記録する |

作業定義に書くのはこの分類だけでよく、個別のケースをどう扱うかは書かなくていい。
