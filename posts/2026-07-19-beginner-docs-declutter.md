## 結論

初学者向け教材で削るべきものは、独立した2つの目線に同じものを見せると一致して浮かび上がる。今回浮かんだ主因は**情報不足ではなく、重複・密度過多・開発者向けドキュメントの混入**だった。

## レビューのやり方

サブエージェント2体を並行で走らせ、同じページ群に対して別の役割を与えた。

- **初学者目線** — 不要・過剰・認知負荷になっている記載の特定
- **ベテラン教材制作者目線** — 完成度と、そぎ落とすべき記載

返してもらう形式は「ファイル:行 / 理由 / 改善案」に固定した。結果、2つの独立レビューの指摘は**強く一致**した。一致した指摘は確度が高いのでそのまま直し、再設計を伴う重いもの（章の減量、法令の条番号の脚注化、導線の三重整理など）は issue に優先度付きで記録して見送った。

## 実際に削ったもの

| 種類 | 内容 |
|---|---|
| 誤情報 | 用語集に残っていた「（準備中）」表記 — 該当ページはすでに公開済み |
| ネタバレ・重複 | 事例概要ページの「加工方針 早見表」を削除。結論を先に見せてしまっていた |
| 二重説明 | 「なぜこの手法を選ぶか」の説明が概要と本文で重複 → 概要側に統合 |
| 開発者情報の漏れ | 設定値の実リテラル、Notebook の「Colab 互換（開発者向け）」注記 |
| jargon | 定義せずに使っていた専門用語の脇道を削除、必要な語は用語集に追加 |
| 整合 | 同種ページで見出しの付け方がばらついていたので統一 |

「開発者向け情報の漏れ」が思ったより多かった。書いている側は仕様と教材を同じリポジトリで扱うので、**受講者に見せる必要のない記述が自然に混ざる**。

## 開発者向けページはナビから隔離する（削除しない）

仕様書は受講者には不要だが、自分たちには要る。mkdocs の **`not_in_nav`** を使えば、ナビゲーションからは外しつつビルドはされ、URL では到達できる。`mkdocs build --strict` で警告ゼロを確認し、隔離したページが URL で健在なことも確認した。

「消す or 見せる」の二択で悩んでいた箇所が、これで片付く。

## トップページは「何が学べるか」を主役にする

同じ日に、トップページの主役を入れ替えた。従来は「1つ目の事例を全7ステップで学ぶ」が主役で、**このサイトの一番の価値である「2種類の加工を学べる」が後回し**になっていた。

具体的な穴もあった。トップの本文から2つ目の事例の「①検討」ページへ入るリンクが存在せず、事例テーブルの行が実装用の Notebook にしか繋がっていなかった。つまり**初学者がトップから2つ目の事例を学び始めると、設計の説明を飛ばしていきなりコードに着地する**。

直し方は、トップ直下に「学べる2つの加工」のカードを置き、両方に「①概要から読む」と「動かす」の2入口を与える。7ステップは「各事例の進め方」として下段へ格下げした。

## 検証

編集後は CI 相当の4ゲートを回した（lint / format / pytest 19 passed / `mkdocs build --strict` 警告ゼロ）。ナビから外す変更はリンク切れを生みやすいので、`--strict` があると安心して削れる。
