## 結論

バックグラウンドのサブエージェントがハングしているかどうかは、**完了通知の `duration_ms` でも transcript ファイルでもなく、そのエージェントが書いている成果物ファイルの mtime** で判定する。

## duration は壁時計

完了通知にはこういう欄が付く。

```
<usage><subagent_tokens>138425</subagent_tokens><tool_uses>38</tool_uses><duration_ms>9099327</duration_ms></usage>
```

9099327ms = 約151分。だが同種の作業の実測レンジは**1件あたり6〜14分**（前バッチの実績で 360〜855秒）で、この件の成果物も他と変わらない量だった。

`duration_ms` は起動から完了通知までの**壁時計時間**で、こちらが次のターンに呼ばれるまでの待ち時間を含む。会話が止まっている間の時間がそのまま乗る。だから「150分経っている＝異常」ではないし、逆に**この数字ではハングを検知できない**。

## 使えなかった判定材料

- **タスクの transcript ファイル**: サイズ 0KB。完了時にまとめて書かれる形式らしく、走行中は空のまま。生存確認に使えない
- **タスクディレクトリの mtime**: 起動時刻のまま更新されない

## 使えた判定材料

エージェントが実際に書いているファイルの mtime。

- 「2分前に成果物を更新」→ 生きている。その中身を見れば、どの段階まで進んだかも分かる
- 「たった今 README を更新」→ 終盤
- 「成果物がまだ1つも無い」→ **序盤か、ハングか、判別できない**

3つ目が落とし穴で、起動直後の件は成果物がゼロなので「1時間更新なし」と表示されて誤検知した。切り分けには**中間生成物**を使った。機械再算出の出力のような、本番の成果物より前に書かれるファイルを見ると、序盤で活動中なのか本当に止まっているのかが分かる。

## 定期チェックの役目はハング検知だけ

15分間隔で自分を起こす仕組み（`ScheduleWakeup`）を入れた。ただし**完了時は自動で通知が来る**ので、定期チェックは「完了の取りこぼし回収」ではない。役目は次の3つ。

1. ハング検知（20分以上無進捗のものをスキップ/再投入の候補にする）
2. 並列数が減っていたら次を投入して埋める
3. 区切りのコミット

完了通知で回るループと、時間で回るループは目的が違う。前者は前進、後者は**前進していないことの検出**。

## ストールしたら「続きから」再投入する

実際に1件、パス指定のタイポで600秒無進捗になった。対処は再投入だが、**最初からやり直させない**。

先に残置状態を調べた。結果は「前段の成果物は生成済み・後段のゲートファイルが未生成・最終段は未実施」で、作業ツリーには余計な残骸も無かった。そこで**後段からの継続**として投入し直したところ、278882ms（約4.6分）で完了した。フル1件ぶんの実測レンジより明確に短い。

再投入されたエージェント自身も、引き継ぎ状況の判定を最初に報告している。

> 前任は②完了・use_cases.md の「UC評価」節も実は記入済み（プレースホルダ残なし）でしたが、③のレビューゲートが未生成でした

「トラッカー上の状態」ではなく「ファイルの実態」から引き継ぎ点を決めさせるのが要点。中断されたエージェントの自己申告は当てにならないが、**ファイルシステムは嘘をつかない**。

## まとめ

| 知りたいこと | 見るもの |
|---|---|
| 生きているか | 成果物ファイルの mtime（数分以内なら生存） |
| 序盤かハングか | 中間生成物の mtime |
| どこまで進んだか | 生成済みファイルの顔ぶれ |
| 正味の処理時間 | `duration_ms` では分からない |
