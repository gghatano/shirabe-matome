## やりたいこと

Claude Code の会話ログはローカルに `.jsonl` として溜まっていく。これを毎日読み返せる形にしたい。ただし全部を自動で公開するのは避けたい。生ログには API キー、絶対パス、案件名など公開できないものが普通に混ざるからだ。

そこで **要約は自動、公開判断は手動** の二段構えにする。

## 全体の流れ

1. **収集** — その日のログを日付で拾う
2. **要約** — トピックごとに分割し、1トピック = 1 Markdown として書き出す
3. **確認** — ドラフト一覧を通知し、公開するものを選ぶ
4. **公開** — 選ばれたものだけをビルドしてデプロイ

## 設計上の肝: 定時ジョブは承認を待てない

素直に書くと「要約 → 確認を待つ → 公開」を一本のジョブにしたくなる。これは動かない。定時ジョブのセッションは処理が終われば落ちるので、人間の返信を待ち続けられない。

なので **2 フェーズに割る**。

```
フェーズ1（定時）  ログ収集 → 要約 → drafts/ に保存 → 一覧を通知 → 終了
                   ↓ （ここでセッションは切れる）
フェーズ2（返信時） drafts/ を読み直す → 選ばれた分を posts/ へ → ビルド → push
```

間をつなぐのは `drafts/YYYY-MM-DD/` に置かれたファイルそのもの。これが仕組みの背骨になる。中間状態をメモリでなくファイルに置くことで、フェーズ間の時間差もセッションの切断も問題にならない。

## 公開範囲の扱い

要約を経由してもセンシティブな情報は漏れるときは漏れる。段階的に進めるのが安全だと考えた。

1. まずローカルに Markdown を書き出すだけの版を作る
2. 数日ぶんを実際に眺めて、公開して問題ない粒度かを確かめる
3. 問題なければ公開段を足す

公開段を足したあとも、`drafts/` にあるものは非公開が既定で、明示的に選んだものだけが `posts/` に移る。デフォルトが「出さない」側に倒れているのが重要で、逆にすると事故ったときに取り返しがつかない。GitHub Pages は削除してもキャッシュや検索インデックスが残る。

## ディレクトリ構成

```
shirabe-matome/
├── posts/          公開すると決めた Markdown（ソース）
├── drafts/         未承認のドラフト（.gitignore 済み）
├── entries/        生成された個別ページ
├── data/           生成された一覧データ
└── build.py        posts/ → entries/ + data/
```

`posts/` だけが人の手で管理される場所で、それ以外は生成物か作業領域。この境界をはっきりさせておくと、あとから要約ロジックを差し替えても壊れない。
